# 工作任务书：汽车电子基本元器件知识库建设 V1.0

## 1. 项目名称

汽车电子基本元器件知识库（Basic Components Knowledge Base）

## 2. 项目背景

为支持后续 BMS 硬件设计、WCCA（Worst Case Circuit Analysis）分析、器件选型、DFMEA 和 AI 辅助硬件开发，需要建立一套系统化、结构化、可持续迭代的基本元器件知识库。

第一阶段采用 Obsidian + Markdown 的方式建设。

知识库不仅需要介绍元器件的基本原理和参数，还需要结合真实制造商 Datasheet，建立参数定义、参数来源、工程应用和 WCCA 计算之间的关联。

知识库由 AI 团队负责建设和维护，关键器件参数和 Datasheet 由用户逐步提供。

## 3. 项目目标

第一阶段完成以下目标：

1. 建立完整的基本元器件分类体系。
    
2. 建立统一的元器件知识文档模板。
    
3. 梳理各类器件的基本参数及其工程意义。
    
4. 说明关键参数在 Datasheet 中的查找方法。
    
5. 结合真实 Datasheet 建立具体器件案例。
    
6. 建立基本元器件与 WCCA 计算参数之间的映射关系。
    
7. 建立适合 Obsidian 使用的目录、索引和双向链接。
    
8. 确保知识库具备持续扩展和后续 AI Skill 调用的能力。

## 5. 统一知识文档要求

所有元器件必须按照统一结构编写。

每类器件至少包含：

### 5.1 基本介绍

- 器件定义
    
- 工作原理
    
- 内部结构或等效模型
    
- 器件分类
    
- 常见封装
    
- 典型应用场景
    

### 5.2 基本参数体系

建立完整参数清单，按照以下类别分类：

- 电气参数
    
- 额定参数
    
- 最大额定值（Absolute Maximum Ratings）
    
- 动态参数
    
- 温度相关参数
    
- 功耗及热参数
    
- 可靠性参数
    
- 其他特殊参数
    

对每个参数说明：

- 英文名称
    
- 中文名称
    
- 符号
    
- 单位
    
- 参数定义
    
- 物理意义
    
- 影响因素
    
- 工程应用场景
    

### 5.3 Datasheet 阅读指南

说明：

- 关键参数位于 Datasheet 哪些章节。
    
- 如何识别 Minimum / Typical / Maximum。
    
- 如何理解参数测试条件。
    
- 如何识别曲线与表格中的限制条件。
    
- 哪些参数是保证值，哪些仅为典型参考值。
    
- 哪些参数需要结合温度、电压和其他工作条件分析。
    

### 5.4 工程设计应用

说明：

- 器件选型原则。
    
- 典型应用电路。
    
- 参数选择注意事项。
    
- 电气应力。
    
- 温度与功耗影响。
    
- 降额设计。
    
- 常见设计错误。
    
- 典型失效模式。
    

### 5.5 WCCA 关联

建立该类器件与 WCCA 的关系：

- 哪些参数需要参与 WCCA。
    
- 每个参数的最大值、最小值如何确定。
    
- 参数受到哪些工作条件影响。
    
- 如何进行温度、偏压、功耗等修正。
    
- 对应的计算公式。
    
- 对应的 Datasheet 数据来源。
    
- 哪些参数不能直接用于计算，需要额外确认。
    

第一阶段先建立参数映射和计算原理，不要求开发完整自动计算程序。

## 6. Datasheet 案例建设要求

用户后续会逐步提供实际 Datasheet。

收到 Datasheet 后，执行以下流程：

1. 识别制造商、产品系列和具体型号。
    
2. 提取器件关键参数。
    
3. 识别参数的 Min / Typ / Max。
    
4. 记录对应测试条件。
    
5. 标注 Datasheet 页码、表格编号或曲线编号。
    
6. 对关键参数进行工程解释。
    
7. 分析参数对电路设计和 WCCA 的影响。
    
8. 建立具体器件案例 Markdown。
    
9. 更新该器件类别的索引。
    
10. 对通用知识中需要补充的内容提出更新建议。
    

每个案例必须保留原始数据来源。

不得将典型值、推测值或未经确认的参数作为制造商保证值。

如果 Datasheet 没有提供必要参数，必须标记为“未提供”或“待确认”，不得自行编造。

## 7. Obsidian 知识库要求

采用 Markdown 文件格式。

要求：

- 使用清晰的层级目录。
    
- 每类器件建立独立入口文档。
    
- 使用 Obsidian 双向链接。
    
- 使用统一文档模板。
    
- 建立首页和分类索引。
    
- 建立 Datasheet 案例索引。
    
- 建立 WCCA 参数关联索引。
    
- 使用 YAML Frontmatter 标记文档类别、版本、状态和关联器件。
    
- 尽可能使用标准英文参数名称，方便后续 AI 检索和 Skill 调用。
    

不要求第一阶段开发 Obsidian 插件。

## 8. 数据准确性与质量要求

这是项目的核心质量要求。

### 8.1 数据来源

优先使用原厂 Datasheet 和官方技术资料。

重点参考制造商：

- Murata
    
- TDK
    
- Panasonic
    
- Vishay
    
- Yageo
    
- Nexperia
    
- Texas Instruments
    
- STMicroelectronics
    
- Infineon
    
- onsemi
    

### 8.2 参数准确性

所有具体参数必须区分：

- Datasheet 保证值
    
- 典型值
    
- 设计参考值
    
- 计算值
    
- 工程假设值
    
- 待确认值
    

### 8.3 可追溯性

涉及具体器件参数时，必须记录：

- Datasheet 文件名称
    
- 制造商
    
- 器件型号
    
- 文档版本或发布日期（如有）
    
- PDF 页码
    
- 参数所在表格或曲线
    
- 测试条件
    

### 8.4 不确定性处理

当资料不足、参数定义不明确或存在不同理解时：

- 不得自行补齐数据。
    
- 标记不确定项。
    
- 说明不确定的原因。
    
- 提出需要用户确认的问题。

由项目管理 Agent 负责：

- 任务拆分。
    
- 任务分配。
    
- 文档结构和模板管理。
    
- 质量检查。
    
- 交付验收。
    
- 问题汇总。
    

由执行 Agent 负责：

- 元器件技术资料研究。
    
- 参数体系整理。
    
- 知识文档编写。
    
- Datasheet 案例提取。
    
- Obsidian 文档维护。
    
- 自检和交付。
    

涉及专业参数定义、计算方法、工程结论时，执行 Agent 必须提供依据，不能只给出结论。

用户负责：

- 提供具体 Datasheet。
    
- 确认有争议的工程参数。
    
- 对重要知识内容进行最终审核。

- 分类合理。
    
- 模板统一。
    
- Obsidian 链接有效。
    

### 内容验收

- 参数体系覆盖主要工程参数。
    
- 参数解释准确。
    
- 有工程应用说明。
    
- 有 Datasheet 阅读指导。

### 数据验收

- 参数来源可追溯。
    
- Min / Typ / Max 区分明确。
    
- 测试条件完整。
    
- 无未经标注的推测数据。
    

### 可扩展性验收

- 可以直接添加新的器件型号案例。
    
- 可以增加新的元器件类别。
    
- 可以被后续 AI Agent 和 WCCA Skill 检索和使用。
    

## 13. 执行约束

1. 第一阶段只建设 Obsidian 知识库，不开发独立软件系统。
    
2. 不要一开始就追求覆盖所有器件，优先保证知识质量。
    
3. 不要将不同器件的数据混在通用知识文档中。
    
4. 通用原理与具体型号案例必须分开存储。
    
5. 不要在没有 Datasheet 依据的情况下填写具体器件保证参数。
    
6. 不要未经用户确认就改变已经确定的目录和知识库架构。
    
7. 每个阶段完成后先提交成果和自检报告，再进入下一阶段。
    
8. 如果发现知识库结构存在明显缺陷，应先提出修改建议，等待确认后再调整。
